# ADR-0002: 施設名検索に Nominatim 公式インスタンスを採用

- 日付: 2026-10-18
- 状態: 採用

## 背景

地点検索は国土地理院の住所検索 API だけで始めた。住所データ主体のこの API では、「東逗子」のような駅名は町名（沼間）と一致しないため候補に出ない。駅や店の名前で目的地を指定できないと、運転前に住所を調べ直すことになる。

必要な能力は 1 つ。日本語の施設名から座標を返すこと。

## 検討した選択肢

- **Nominatim 公式インスタンス**（OSM データ、無料、キー不要）: 駅・店・公園を名前で引ける。利用規約で 1 req/秒以下・オートコンプリート禁止・リクエスト元の識別が条件
- **Nominatim セルフホスト**: 規約の制約は消えるが PostgreSQL + PostGIS が要る。関東の取り込みだけで数 GB・数時間、常駐 1〜2 GB。GraphHopper と同居させるには VPS 増強が要る
- **Photon**（komoot）: オートコンプリート向けだが Java + Elasticsearch でセルフホストはやはり重い。公開インスタンスのデータは Nominatim と同じ OSM
- **静的な駅リスト**: GraphHopper 用の OSM PBF から `railway=station` を抜いて JSON 化し、フロントで絞り込む。外部サービス不要だが駅以外は引けず、範囲も PBF と同じ関東に限られる
- **商用 API**（Google Places / Yahoo! ローカルサーチ）: 精度は最も高いがキー管理と課金が要る。自分用の規模には過剰

## 決定

Nominatim 公式インスタンスを使う。駅以外も引け、サーバを増やさない唯一の選択肢。

規約を守るための設計:

- 施設検索は Enter 確定時だけ呼ぶ。入力中の候補は従来どおり国土地理院の住所検索
- アプリ側で前回リクエストから 1 秒空ける
- リクエスト元の識別はブラウザが送る `Referer`（公開ドメイン）に任せる
- 候補リスト末尾に「© OpenStreetMap contributors」を出す

## 影響

- 検索欄に「入力中は住所、Enter で施設」という 2 つの経路ができる。UI 上は同じ候補リストに出すので操作は変わらない
- 公式インスタンスが止まる・規約が変わると施設検索だけが使えなくなる。地図タップで代替できるので経路探索は止まらない
- 表記ゆれ・かな入力には弱い。不足を感じたら静的な駅リストを足す（上の選択肢）
